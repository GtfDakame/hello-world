# ADR-001: Синхронизация данных и разрешение конфликтов

**Статус:** Proposed  
**Дата:** 2024-01-15  
**Автор:** Backend Architect  
**Обсуждение:** [GitHub Discussion #1](#)

---

## Контекст

Мессенджер требует надежной синхронизации сообщений между множественными устройствами пользователя с поддержкой offline-first архитектуры. Конфликты возникают при:
- Одновременном редактировании сообщений на разных устройствах
- Удалении сообщений при отсутствии соединения
- Изменении метаданных чата (название, участники)

## Решение

Принята гибридная стратегия синхронизации:

### 1. Операционные трансформации (OT) для текста сообщений
**Обоснование:**
- OT хорошо изучен и проверен в production (Google Docs, Firebase)
- Оптимальная производительность для текстовых операций
- Детерминированное разрешение конфликтов

**Реализация:**
```go
type Operation struct {
    Type      OpType    // INSERT, DELETE, RETAIN
    Position  int
    Content   string
    Timestamp int64
    DeviceID  string
}

type Document struct {
    Content   string
    Version   int64
    Operations []Operation
}
```

### 2. CRDT для метаданных и состояний
**Обоснование:**
- CRDT гарантируют eventual consistency без координации
- Идеально для булевых флагов, счетчиков, наборов участников
- Нет центрального сервера для разрешения конфликтов

**Типы CRDT:**
- **G-Counter:** Счетчики прочитанных сообщений
- **PN-Counter:** Балансы, рейтинги
- **OR-Set:** Участники чата, реакции
- **LWW-Register:** Последняя запись выигрывает (название чата)

### 3. Версионирование состояния
Каждое сообщение и объект получает векторные часы:

```go
type VectorClock map[string]int64 // device_id -> counter

type Message struct {
    ID          string
    Content     string
    AuthorID    string
    ChatID      string
    Timestamp   int64
    VectorClock VectorClock
    Signature   []byte
}
```

```
│   Client    │◄───────►│   Server    │

       │                        │

       │  (Redpanda)            │  (Kafka)
       ▼                        ▼
┌─────────────┐         ┌─────────────┐
│  CRDT Store │         │  OT Server  │
│  (Redis)    │         │  (Go)       │
└─────────────┘         └─────────────┘
```

## Протокол синхронизации

### 1. Handshake при подключении
```
Client → Server: SYNC_REQUEST {last_vector_clock, device_id}
Server → Client: SYNC_RESPONSE {delta_operations, new_vector_clock}
Client → Server: SYNC_ACK {applied_count}
```

### 2. Отправка сообщения
```
1. Клиент создает локальную операцию
2. Применяет к локальному состоянию
3. Отправляет на сервер через WebSocket
4. Сервер валидирует, применяет, рассылает другим устройствам
5. Клиент получает подтверждение с глобальным version
```

### 3. Разрешение конфликтов
```
При получении удаленной операции:
1. Сравнить vector clocks
2. Если операция старше локальной → игнорировать
3. Если операция новее → применить
4. Если concurrent → применить OT transform
5. Обновить vector clock
```

## Последствия

### Положительные
- ✅ Гарантированная согласованность в конечном счете
- ✅ Работа без соединения не ограничена
- ✅ Масштабируемость (нет блокировок)
- ✅ Детерминированное поведение

### Отрицательные
- ⚠️ Увеличенный размер метаданных (vector clocks)
- ⚠️ Сложность отладки распределенных систем
- ⚠️ Требуется обучение команды

### Нейтральные
- ➖ Необходимость миграции существующих данных
- ➖ Мониторинг sync latency

## Альтернативы

### 1. Центральный сервер авторитета
**Отклонено:** Нарушает offline-first принцип, single point of failure

### 2. Last-write-wins для всего
**Отклонено:** Потеря данных при конфликтах, плохой UX

### 3. Блокировки на уровне объектов
**Отклонено:** Не работает offline, высокая задержка

## План внедрения

1. **Неделя 1-2:** Прототип OT для текста
2. **Неделя 3-4:** Реализация CRDT библиотек
3. **Неделя 5-6:** Интеграция с клиентскими хранилищами
4. **Неделя 7-8:** Нагрузочное тестирование (10k concurrent ops/sec)
5. **Неделя 9-10:** Beta testing с реальными сценариями

## Метрики успеха

| Метрика | Target | Измерение |
|---------|--------|-----------|
| Sync latency (p95) | <100мс | От операции до подтверждения |
| Conflict rate | <1% | Отношение конфликтов к операциям |
| Data loss | 0% | При normal operation |
| Offline duration support | ∞ | Без потери данных |
